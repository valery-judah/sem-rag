# Python Coding and Domain Modeling Conventions

## Philosophy
To ensure strict correctness, type safety, and maintainability across the project, all future implementations—especially those generated by agents—must adhere to strict domain modeling rules. The primary goal is to **avoid primitive obsession** and rely on the type system and validation boundaries to enforce constraints.

## Domain Modeling Rules

### 1. Avoid Primitive Obsession
Do not pass raw primitives (like `str`, `int`, `dict`) around the system if they represent a specific domain concept. Instead, wrap them in a strong type. For example, instead of passing a raw `str` for an identifier, use a dedicated type like `CorpusId`.

### 2. Strong Typing with `NewType` and `Annotated`
For simple wrapper types (e.g., strings that represent identifiers or specific formats), use Python's `NewType` combined with `typing.Annotated` and Pydantic's `AfterValidator` to enforce validation logic. This ensures the type is validated when used in Pydantic models, and checked correctly by static type checkers.

**Pattern Example:**
```python
from typing import Annotated, NewType
from pydantic import AfterValidator, Field

# 1. Define the internal NewType (private)
_DomainId = NewType("_DomainId", str)

# 2. Write a validation function returning the NewType
def validate_domain_id(value: str) -> _DomainId:
    if not value.isalnum():
        raise ValueError("Domain ID must be alphanumeric")
    return _DomainId(value)

# 3. Export the public Annotated type for use in type hints and Pydantic models
DomainId = Annotated[
    _DomainId, 
    Field(min_length=1), 
    AfterValidator(validate_domain_id)
]

# 4. Optional: Provide a parsing helper for manual instantiation
def parse_domain_id(value: str) -> _DomainId:
    return validate_domain_id(value)
```

### 3. Pydantic for Complex Domain Models
For structured data, entities, and aggregates, use Pydantic `BaseModel`.
- Prefer immutable models (`frozen=True`) where applicable to prevent accidental side effects.
- Use explicit types (including the strong `Annotated` types defined above) for all fields.
- Validate complex, cross-field dependencies using `@model_validator(mode='after')`.
- Fail fast at the boundaries: let Pydantic handle incoming validation so the core domain can trust its inputs.

### 4. Strict Typing and Static Analysis
- All functions and methods must have complete type hints for parameters and return types.
- Missing return types (e.g., `def do_something():` instead of `def do_something() -> None:`) are not allowed.
- Validate type correctness locally using `uv run poe type` before committing or assuming completion.
- Never use `typing.Any` for new code unless interfacing with an untyped external library. Cast or validate external data into a domain type immediately.
- Avoid `# type: ignore` unless it is a known static analysis limitation, and always include a comment explaining why it is necessary.

### 5. Error Handling
- Validate early: validators should raise standard `ValueError` or specific exceptions if data violates domain rules.
- Do not swallow exceptions silently. Log them or let them bubble up to the application's defined error handlers.
- Create distinct exception classes for domain errors rather than relying on `Exception` or generic built-ins.

### 6. Architectural Layers
- Keep domain types and validators cohesive (e.g., in `domain.py`, `models.py`, or `identifiers.py` modules).
- Strictly separate pure domain logic from IO, network, or persistence logic (which belongs in repositories or services).
